## Description

### Goal

Enable live view development in Claude.ai: when a developer edits `View.tsx`, the change appears in Claude.ai's MCP Apps iframe within seconds, without manual rebuild/redeploy.

Currently views load from S3/CDN (static — requires `kitstack build` + `kitstack deploy` to update). This ticket adds a relay path for **kit-specific files only** (View.tsx, CSS) while keeping React and shared deps on CDN.

### Background: How views render in Claude.ai

1. Claude calls `kit_view(view="pipeline")` → MCP handler runs the loader, returns JSON data + shell HTML as an MCP embedded resource
2. Claude.ai renders the shell HTML in a sandboxed iframe
3. The shell loads `vendor.js` (React) + `shared.js` (SDK hooks) via `<script>` tags from CDN
4. The shell loads the per-view module (`pipeline.js`) from CDN and calls `mount(container, data)`
5. The React component renders with the pre-loaded data

### Background: The relay architecture

The dev server (`kitstack dev` without `--stdio`) connects to a WebSocket relay:

```
Developer's machine ←→ WebSocket (DevRelay API Gateway) ←→ McpRouter Lambda ←→ Claude.ai
```

- **MCP requests** (tools/call, kit_view, etc.) flow through the relay successfully
- **Asset requests** can also flow through the relay: McpRouter has a `GET /dev/{sessionId}/**` route that sends asset requests to the CLI via WebSocket, the CLI fetches from local Vite dev server and responds

### The problem we solved partially

We tried relaying ALL view assets through the WebSocket. It worked for small files but **crashed the connection** because:

- `react-dom_client.js` from Vite is **~1MB** 
- API Gateway WebSocket has a **128KB message size limit** and **32KB frame size limit**
- Sending 1MB as a JSON-wrapped WebSocket message kills the connection

### The solution: hybrid CDN + relay

**React (vendor.js ~188KB) and SDK hooks (shared.js ~2KB) load from CDN** — they never change during development.

**Kit-specific files load through the relay** — they're tiny and change frequently:
- Per-view entry `.tsx` files: ~3-4KB each
- View component `View.tsx`: ~3-20KB each  
- `styles.css` (as Vite JS module): ~12KB

The key insight: **Vite dev server serves View.tsx as a transformed JS module**. It imports React from `/node_modules/.vite/deps/react.js`. We need to **rewrite those imports** to point to the CDN vendor.js instead of Vite's React.

### What exists already

1. **McpRouter GET route** (`packages/mcp-server/src/router/handler.ts` ~line 432): handles `GET /dev/{sessionId}/**` — forwards to CLI via WebSocket, polls DynamoDB for response, returns it. CORS headers included. All error paths return `Access-Control-Allow-Origin: *`.

2. **Relay client asset handler** (`packages/sdk/src/runtime/relay-client.ts` ~line 86): handles `type: "asset"` messages from WebSocket — fetches from local Vite dev server, returns `{ status, contentType, body }`.

3. **Import path rewriting** (same file, ~line 95): rewrites absolute import paths in JS responses to include `/dev/{sessionId}/` prefix so sub-imports go through the relay route. Patterns: `from "/..."`, `import("/...")`, `import "/..."`.

4. **Dev shell HTML generator** (`packages/sdk/src/runtime/mcp-handler.ts`, `generateDevRelayShell` function ~line 794): generates a shell that loads view modules from a relay URL instead of CDN.

5. **MCP handler config** has `devAssetBaseUrl` option — when set, `kit_view` uses the dev shell + includes relay domain in CSP.

6. **Vite dev server** is already started in relay mode (`packages/sdk/src/cli/commands/dev.ts` ~line 179) with generated entry points per view in `.kitstack/devkit-entries/`.

### What needs to change

#### 1. Externalize React in the Vite dev server config

The generated `vite.config.ts` in `.kitstack/devkit-entries/` needs to externalize React so Vite doesn't serve its own copy. Instead, the entry points should import from the CDN `vendor.js` which the shell already loads via a script tag.

**Option A**: Use `resolve.alias` to point `react` and `react-dom` to the CDN URL:
```typescript
// Won't work — Vite can't alias to an HTTP URL
```

**Option B**: Use `define` to replace React imports with window globals:
```typescript
// The shell loads vendor.js which registers React on a global
// Entry points use React.createElement — no import needed if React is global
```

**Option C** (recommended): Keep Vite serving React but **don't relay the React files**. The relay client checks file size before sending — if over 100KB, skip it and let it load from CDN. The shell loads vendor.js from CDN as a `<script>` tag which makes React available globally. The per-view module uses React from that global.

But this won't work because ES module `import { useState } from "react"` is different from a script tag global.

**Option D** (most practical): The import rewriting in the relay client should rewrite React imports to point to the CDN URL instead of the relay URL:
```javascript
// Before rewrite:
import React from "/node_modules/.vite/deps/react.js?v=abc"
// After rewrite (current — broken, file is 1MB):
import React from "/dev/67c99a1f/node_modules/.vite/deps/react.js?v=abc"
// After rewrite (new — points to CDN):
import React from "https://d3m7hzbfloe6y2.cloudfront.net/apps/kits/crm/vendor.js"
```

The relay client needs to know the CDN URL for vendor.js and shared.js so it can redirect React/react-dom imports there.

#### 2. Re-enable `devAssetBaseUrl` in the dev command

Currently disabled at `packages/sdk/src/cli/commands/dev.ts` ~line 252. Re-enable it:
```typescript
const handler = createMcpHandler({ 
  kit, db, 
  platformCdn,
  kitCdn: kitCdnUrl,
  devAssetBaseUrl: `${mcpBaseUrl}/dev/${sessionId}`,
});
```

#### 3. Update CSP in kit_view response

The `_meta.ui.csp.resourceDomains` must include BOTH the McpDomain (for relayed assets) AND the CDN domain (for vendor/shared). This is already implemented in `handleKitView` (~line 583) and `resources/read` (~line 710).

#### 4. File watcher for auto-rebuild

When a file in `src/views/` changes, Vite's dev server already picks it up (HMR). The relayed modules will automatically be fresh on the next `kit_view` call because the relay fetches from Vite in real-time.

However, the user needs to re-trigger `kit_view` in Claude.ai to see the change (no push mechanism from relay to iframe). This is acceptable — the developer asks Claude to "show the pipeline view again" and gets the updated version.

### Critical constraints

1. **API Gateway WebSocket message limit: 128KB.** Any single relay response must be under this. React is 188KB — CANNOT go through relay. Per-view modules are 3-20KB — fine.

2. **CORS**: The McpRouter Lambda URL has `url: { cors: false }` — we handle CORS manually. All responses (success AND error) must include `Access-Control-Allow-Origin: *`. Claude.ai's iframe origin is `*.claudemcpcontent.com`.

3. **Shell HTML is embedded in MCP response**, not loaded from a URL. The `kit_view` tool result contains the shell as an inline `EmbeddedResource` with MIME type `text/html;profile=mcp-app`. CSP is declared in `_meta.ui.csp` on the resource.

4. **Vite transforms absolute paths**: `import "../../src/views/styles.css"` becomes `import "/src/views/styles.css"`. The relay client rewrites these to `/dev/{sessionId}/src/views/styles.css` so they go through the relay route. BUT: React imports (`/node_modules/.vite/deps/react.js`) must be redirected to CDN, NOT relayed.

5. **Duplicate React instances crash hooks**: If the shell loads vendor.js (React) from CDN via `<script>`, and the view module imports a different React from Vite, hooks fail with "Invalid hook call". All React must come from ONE source.

6. **The `$default` WebSocket handler** (`packages/mcp-server/src/relay/default.ts`) stores responses in **DevRelayStore** DynamoDB table (not MCPAuthStore). The McpRouter polls DevRelayStore with `ConsistentRead: true`.

## Work Log

### 2026-04-26 — Implementation (Option D: CDN vendor redirect)

**Approach**: Relay client rewrites Vite's React/ReactDOM imports to CDN vendor.js URL. All other imports go through relay as before. vendor.js (192KB) loads directly from CDN, bypassing the 128KB WebSocket limit.

**Key insight**: `minifyInternalExports: false` in the Rollup build preserves original export names (`useState`, `createRoot`, `jsx`, etc.) in vendor.js, making it import-compatible with Vite's pre-bundled `react.js`.

**Files changed**:

1. `packages/sdk/src/build.ts` — Added `minifyInternalExports: false` to Rollup output config. Added `_vendor_reexports.ts` entry that forces ALL React exports into vendor.js (so any `import { X } from "react"` in dev works).

2. `packages/sdk/src/runtime/relay-client.ts` — Added `cdnVendorUrl` option. Import rewriting now has two steps: (1) redirect React/ReactDOM/jsx-runtime imports to CDN vendor.js, (2) prefix remaining absolute imports with relay base path. Regex pattern `react(?:\.js|-dom|_jsx)` matches react.js, react-dom_client.js, react_jsx-runtime.js but NOT react-router or react-query.

3. `packages/sdk/src/cli/commands/dev.ts` — Re-enabled `devAssetBaseUrl` on the MCP handler (was disabled). Passes `cdnVendorUrl` (`${platformCdn}/vendor.js`) to relay client.

4. `packages/sdk/src/devkit/server.ts` — Added `jsxDev: false` to Vite esbuild config so JSX uses production `jsx`/`jsxs` from `react/jsx-runtime` (matching CDN vendor.js) instead of dev-only `jsxDEV`.

**No changes needed**: `mcp-handler.ts` — CSP already includes both relay origin and platformCdn. `generateDevRelayShell` loads view modules from relay URL; their React imports are rewritten by the relay client.

**Requires rebuild+deploy**: After pulling these changes, run `kitstack build && kitstack deploy` once to get vendor.js with unminified exports on CDN.
