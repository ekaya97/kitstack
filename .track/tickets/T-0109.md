## Description

Plan: docs/company-pivot-plan.md:29-61. KitStack is pivoting to a company-internal MCP tool; only the operator deploys kits.

CURRENT: web/src/app/api/cli/deploy/route.ts gates only on authenticateCli() (route.ts:47-68) = any valid CLI session token (session.userAgent = kitstack-cli). No role check. Admin concept exists: user.role enum [user,admin] in web/src/db/auth-schema.ts:12; requireAdmin() in web/src/lib/admin-auth.ts:8 (used only by admin dashboard).

CHANGES:
1. In the deploy route, after authenticateCli(), load the users role from userTable (auth query at route.ts:61-66 is nearby) and return 403 unless role === admin.
2. Apply the same guard to any other mutating /api/cli/* route (registry seed, kit upsert). /api/cli/token (web/src/app/api/cli/token/route.ts) stays open — a non-admin token can no longer do anything privileged.
3. Friendly 403 error branch in the CLI: packages/sdk/src/cli/commands/deploy.ts:134-141.
4. Set the operator account (<operator email>) role=admin via an UPDATE migration/seed. NEVER use DROP statements in any SQL.
5. Remove user-facing deploy affordances from docs pages / onboarding copy that advertise kitstack deploy.

ACCEPTANCE: non-admin CLI session gets 403 with clear message; admin session deploys successfully; unit test for the guard.
