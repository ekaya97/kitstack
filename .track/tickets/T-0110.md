## Description

Plan: docs/company-pivot-plan.md:64-103. NOTE: there are NO per-user VPC links/NLBs anywhere — kit dispatch is direct lambda.invoke() from the MCP router. What exists is a shared no-internet sandbox for untrusted kit code; with owner-only deploys (WS1) it is pure cost/complexity, and removing it gives kit Lambdas outbound internet + scoped IAM (required by the freelancer kit: Bedrock embedding calls, page fetching).

CHANGES:
1. Delete kitVpc and lambdaEndpoint from infra/mcp.ts:39-53 (shared sst.aws.Vpc, Lambda interface endpoint ~7 USD/mo).
2. Drop subnetIds/securityGroupIds from the KitLambdaInfra linkable (infra/mcp.ts:99-101).
3. Remove the AWSLambdaVPCAccessExecutionRole managed-policy attachment (infra/mcp.ts:72-75).
4. Remove the vpcConfig branch from packages/sdk/src/deploy/deploy-lambda.ts (lines 34-40, 96-98, 153, 185).
5. OPTIONAL simplification: the invocation-token -> DB-creds proxy indirection (packages/mcp-server/src/router/handler.ts:137-193, handleDbProxy) existed because sandboxed kits could not be trusted with raw creds; tool-dispatcher.ts:174-186 already passes dbUrl/dbToken directly. The proxy path can be deleted if nothing else consumes it — verify the generated kit runtime does not call it before removing.

The production CLI deploy route already creates kit Lambdas WITHOUT VpcConfig (web/src/app/api/cli/deploy/route.ts:230-235), so no deployed-kit changes needed.

ACCEPTANCE: sst deploy succeeds with VPC resources gone; a test kit Lambda can fetch an external URL.
