## Description

Plan: docs/company-pivot-plan.md:134-160. Infra half of kit jobs (SDK half: T-0111).

WHY A DISPATCHER: schedules cannot target kit Lambdas directly because DB credentials are per-activation (per user now, per org after WS5).

1. New infra/jobs.ts: JobDispatcher Lambda. On fire with payload {kitId, jobName}:
   - Query active activations for the kit: DynamoDB UserKitDbs today (packages/mcp-server/src/db/dynamo.ts:69-130); coordinate with the WS5 OrgKitDbs ticket (T-0115) — abstract the lookup so switching key from userId to orgId is one function change.
   - For each activation: async-invoke Kit-{kitId} (InvocationType Event) with { type: job, jobName, orgId/userId, dbUrl, dbToken }. Per-activation error isolation.
   - Support ctx.continue: kit handler can request re-invocation with a continuation payload; cap at N continuations per firing (e.g. 20).
   - Emit metrics; wire failure counts + runaway continuations into the existing kill-switch alarm system (infra/mcp.ts:265-328) so a buggy job cannot burn money overnight.
2. Schedule sync in web/src/app/api/cli/deploy/route.ts: after Lambda provisioning, read manifest jobs array; create/update/delete EventBridge Scheduler schedules named ks-job-{kitId}-{jobName} targeting the dispatcher. Grant the web app scheduler permissions on the ks-job-* namespace in infra/web.ts (pattern: existing lambda grants at web.ts:18-30).
3. Apply manifest resources { memoryMb, timeoutSeconds } in the deploy route Lambda provisioning (route.ts:230-243) instead of hardcoded 128MB/10s; keep current values as defaults.

ACCEPTANCE: deploying a kit with a job creates the schedule; firing it runs the job handler against the right DB; removing the job from the kit deletes the schedule; job failure shows in metrics/kill-switch path.
