## Description

Plan: docs/company-pivot-plan.md:410-465 (Design points 3, 4). Re-key kit databases from per-user to per-org so org members share the same Turso DB.

CURRENT: DB per (user, kit) named ks-{userId}-{kitId} (web/src/services/turso-provisioner.ts:71); creds in DynamoDB UserKitDbs keyed (userId, kitId) (packages/mcp-server/src/db/dynamo.ts:69-130); MCP dispatch fetches via getUserKitDb(userId, kitId) (packages/mcp-server/src/router/tool-dispatcher.ts:148) and passes dbUrl/dbToken into the kit Lambda invocation (tool-dispatcher.ts:174-186).

CHANGES:
1. New DynamoDB table OrgKitDbs (hash orgId, range kitId), same item shape, in infra/mcp.ts (pattern: userKitDbs at mcp.ts:19-22). Link to router + web.
2. Provisioners take orgId: web/src/services/turso-provisioner.ts and packages/mcp-server/src/framework/db-provisioner.ts:117-135; naming ks-org-{orgId}-{kitId}. Activation flow (web/src/services/kit-lifecycle.service.ts) activates for the ACTIVE ORG, gated on org role admin/owner.
3. MCP dispatch resolution (tool-dispatcher.ts): JWT sub stays userId. Resolve userId -> org for the kit: orgs where user is a member AND org has the kit activated; if exactly one use it; if multiple prefer an active_org claim in the JWT (org picker on the OAuth consent screen — authorize flow in packages/mcp-server/src/router/handler.ts:229-291, session params already stored in OAuthStore). Cache membership lookups (in-Lambda TTL cache is fine). View loaders resolve the same way (packages/mcp-server/src/router/platform-adapter.ts:105-129), and AppData (packages/mcp-server/src/app-data/handler.ts).
4. Migration script: for each UserKitDbs row, map userId -> personal orgId (from T-0114 backfill) and write OrgKitDbs row. Turso DBs themselves do not move — only the pointer records. Keep UserKitDbs read path as fallback until migration verified, then remove.
5. Coordinate with T-0112 (JobDispatcher) — it enumerates activations; switch its lookup to OrgKitDbs.

Concurrency is a non-issue: Turso is server-side, multiple users on one DB is fine.

ACCEPTANCE: two users in one org see the same kit data over MCP; personal-org users unaffected; activation by org admin provisions ks-org-* DB; migration script idempotent.
