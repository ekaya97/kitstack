## Description

Plan: docs/company-pivot-plan.md:440-465 (Design points 5, 6). The Zanzibar-style tuple engine (packages/authz) already has team in the SubjectType union (packages/authz/src/types.ts:1) but nothing exercises it outside tests.

CHANGES:
1. packages/authz/src/types.ts: add object type organization; add relations owner, admin, member (existing: subscriber, activator, author on subscription, kit, review).
2. Membership tuples: when org membership changes (T-0114 plugin hooks or service layer), write/revoke (user U, member|admin|owner, organization O) tuples via grantRelation/revokeRelation (packages/authz/src/lifecycle.ts:11-56).
3. Kit entitlement becomes a team-subject tuple on activation: (team O, activator, kit K) — kit-lifecycle.service.ts:175,227,288 currently grants with default subjectType user; switch to team with the org id.
4. Extend check() (packages/authz/src/engine.ts:12-30) with ONE level of indirection: check(user U, activator, kit K) = direct tuple OR exists org O where (U, member|admin|owner, O) AND (team O, activator, K). Keep it a single SQL join, not a general userset-rewrite engine.
5. MCP runtime uses this via mcpCheckTuple (packages/mcp-server/src/router/authz.ts:50-67) -> tool-dispatcher.ts:108-125 — verify the indirection works on that path.
6. Tool-level access control: org role available in ctx for the SDK authorize(args, ctx) hook (AuthzRequirement in packages/sdk/src/types.ts:77) so kits can mark admin-only tools. Minimal plumbing: pass the resolved org role in the kit invocation payload.
7. Tests in packages/authz/tests (engine.test.ts already has team-subject cases at lines 48-60,124-126 — extend for indirection).

ACCEPTANCE: member of an org with an activated kit passes the dispatcher authz check with no direct user tuple; removing membership revokes access; unit tests for indirection + revocation.
