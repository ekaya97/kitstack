## Description

Plan: docs/company-pivot-plan.md:173-268 (esp. 3.1-3.3). The company deliverable. New kit at kits/freelancer-search following the anatomy of kits/crm (kit.config.ts with defineKit, src/schema.ts drizzle, migrations/ via drizzle-kit + hand-written SQL for FTS5/vector, src/instructions.ts, src/tools, src/views).

DATA POSTURE (important): both portals (freelancermap.de, freelance.de) expose PUBLIC teaser profiles without contact data; their business model is contact unlock. We store only what the public profile shows, always keep source URLs, and NEVER store attachment files — attachments are read once for embedding (see T-0118) and only the portal-hosted file URL is kept.

SCHEMA (plan 245-267): freelancers (canonical), freelancer_sources (unique on portal+portal_profile_id, content_hash, first/last_seen_at), documents (portal_file_url, embedding F32_BLOB + libsql_vector_idx, content_hash — NO file bytes, NO extracted text), freelancer_fts (FTS5 over name/headline/skills/summary), freelancer_embeddings (F32_BLOB(1024) + libsql_vector_idx), merge_candidates, scrape_runs (doubles as job cursor store). Turso/libSQL supports FTS5 and native vector (vector_top_k, vector_distance_cos) with no extensions. CAVEAT: build-time migration validation runs against in-memory libSQL and forbids DROP (packages/sdk/src/build.ts:176-184) — verify FTS5 virtual tables + libsql_vector_idx statements pass; if not, add a narrow validation escape hatch in the SDK. NEVER use DROP in migrations.

JOBS (needs T-0111 defineJob; iterate locally with T-0113 kitstack job run): scrape_freelancermap (nightly 02:00), scrape_freelance_de (nightly 03:00). Each: paginated public listing -> profile detail fetch -> cheerio parse -> normalize -> upsert freelancer_sources (+ provisional freelancers row for new profiles). Politeness: 1-2 req/s per host, backoff, honest UA, robots.txt. Incremental: skip profiles with last_seen_at < N days. Long crawls: cursor in scrape_runs + ctx.continue(). Profiles gone from portal on later crawls: mark/drop (GDPR hygiene, plan 240-242). FIRST STEP: manually verify both portals render server-side (cheerio-parseable); if JS-rendered, isolate fetch behind an interface and note Playwright-container fallback. Optional: raw HTML snapshots to S3 for reparse (plan 205-208) — skip in v1 if it adds friction.

Embedding/dedupe pass is T-0118; search tools T-0119; views T-0120. Keep schema stable for those tickets.

ACCEPTANCE: kitstack job run scrape_freelancermap against dev DB ingests real profiles end-to-end; re-run is idempotent (content_hash); migrations build clean; unit tests for parsers on fixture HTML.
