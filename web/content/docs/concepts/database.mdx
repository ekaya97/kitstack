# Database

Every kit gets a per-user SQLite database. Not row-level isolation — **completely separate databases**. You define the schema in TypeScript with Drizzle ORM, and the SDK handles provisioning, migrations, and connection management.

## Per-user isolation

When a user activates your kit, the platform provisions a dedicated SQLite database for that user. No shared tables, no tenant columns, no access control queries. User A's data is physically separated from User B's data.

In development, the database is a local file at `.kitstack/dev.db` in the kit directory. On the hosted platform, each user gets an isolated Turso database, regularly backed up. A self-hosted server uses the one database URL you give it (see [Self-hosting](/docs/guides/self-hosting)).

## Schema as source of truth

Your Drizzle schema file is the canonical definition of your database:

```ts filename="src/schema.ts"
import { sqliteTable, text, real, integer } from "drizzle-orm/sqlite-core";

export const expenses = sqliteTable("expenses", {
  id: text("id").primaryKey(),
  date: text("date").notNull(),
  description: text("description").notNull(),
  amountGross: real("amount_gross").notNull(),
  category: text("category").notNull(),
  createdAt: integer("created_at", { mode: "timestamp" }).notNull(),
});

```

`kit.config.ts` imports the module as a whole (`import * as schema from "./src/schema"`). The schema is passed to `defineKit()` and powers type-safe queries in your tool handlers and view loaders.

## Migrations

Migrations are derived from the schema, not written by hand. The `migrations/` directory contains SQL files generated by `drizzle-kit`:

```bash filename="Terminal"
# Edit src/schema.ts (add a column, table, etc.), then any of:
npm test                                   # drizzle-kit generate && vitest run
npx kitstack call kit my-kit list_items '{}'
npx kitstack dev --local
```

When `drizzle.config.ts` exists in your kit root, `kitstack dev`, `kitstack call`, and `kitstack build` run the kit's `drizzle-kit generate` before proceeding (`dev` and `call` report a new migration as one line on stderr). `npm test` generates them through the scaffolded script. `kitstack serve` only applies existing migrations. New migration files appear in `migrations/`.

Your kit references the directory in `kit.config.ts`:

```ts filename="kit.config.ts" highlight={4}
export default defineKit({
  id: "my-kit",
  // ...
  schema,
  migrationsDir: "./migrations",
});
```

A relative `migrationsDir` is resolved against the kit directory. The `migrations/` directory is committed to git. It's a build input, not a build output.

### Raw SQL alternative

If you prefer raw SQL (or another ORM), use the `migrationSql` field instead:

```ts filename="kit.config.ts"
export default defineKit({
  id: "my-kit",
  // ...
  migrationSql: `
    CREATE TABLE IF NOT EXISTS items (
      id TEXT PRIMARY KEY,
      name TEXT NOT NULL,
      created_at INTEGER NOT NULL
    );
  `,
});
```

`migrationSql` takes precedence if both fields are provided.

## ctx.db

Every tool handler, `load` function, and view loader receives the request context `ctx` (type `KitContext`). The database is `ctx.db`:

| Field | Description |
|-------|-------------|
| `ctx.db` | A Drizzle (libSQL) database for the kit — scoped to the current user on the hosted platform. Use your schema for type-safe queries. |
| `ctx.identity` | `{ principal, actor }` — who is calling. |
| `ctx.params` | Request parameters supplied by the host (for example, view parameters). |
| `ctx.connectors` | Connector clients bound by the host (`get`, `require`, `has`). |
| `ctx.log`, `ctx.telemetry`, `ctx.audit` | Logging and metadata-only telemetry/audit sinks. |

```ts filename="src/tools/add-expense.ts"
handler: async (ctx, args) => {
  const id = crypto.randomUUID();
  await ctx.db.insert(expenses).values({ id, ... });
  return kit.result(kit.created(id, "expense", "Expense added."));
},
```

You never manage connections, credentials, or user routing — the SDK handles it.

## Runtime behavior

| Context | What happens |
|---------|-------------|
| `kitstack dev`, `kitstack call` | Run `drizzle-kit generate`, then apply all migrations to `.kitstack/dev.db` |
| `npm test` | The script runs `drizzle-kit generate`; `createTestKit()` then applies all statements to an in-memory SQLite database |
| `kitstack build` | Same generate step, copies `migrations/` into the build output, validates SQL |
| `kitstack serve` | Applies existing migrations to its database; does not generate |
| `serve()` | Applies nothing — see [Self-hosting: migrations](/docs/guides/self-hosting#migrations) |
| Hosted platform | The platform applies pending migrations per-user |

## Schema iteration during development

<Note>
`kitstack dev` records which migration statements already ran against the local database, so each runs once, including `ALTER TABLE` changes. `kitstack dev --local --reset-db` recreates the database from scratch (this deletes local dev data).
</Note>

## Build-time validation

`kitstack build` validates your migration SQL against a fresh in-memory SQLite database:

- Each SQL statement is executed to verify syntax
- `DROP` statements are **rejected** with error code `MIGRATION_DROP_FORBIDDEN`
- Statement count is reported in the build output

<Warning>
DROP statements are forbidden in migration SQL. This is a hard rule — not configurable. If you need to remove a column or table, create a new table with the desired schema and migrate data.
</Warning>

## Gotchas

**Migration SQL splitting is naive.** The migration runner splits SQL on `;` characters. Semicolons inside string literals or trigger bodies will break it. In practice, kit migrations are simple DDL that never contains embedded semicolons.

**`IF NOT EXISTS` is auto-injected in dev mode.** The dev database provisioner automatically adds `IF NOT EXISTS` to `CREATE TABLE` statements.

**`reset()` in tests does not re-run migrations.** The `createTestKit().reset()` method uses `DELETE FROM` on each table — it clears data but keeps the schema. If your migrations include `INSERT` seed data, that data won't be re-seeded after `reset()`.
