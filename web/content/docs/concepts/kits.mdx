# Kits

A kit is a lightweight MCP app that gives an LLM domain-specific capabilities. It packages tools, views, a database schema, and system instructions into a single deployable unit that any MCP-compatible client can connect to.

Think of kits as apps on an app store. They're focused utility tools — not full-blown software. A CRM, an expense tracker, a sequence builder. They bridge the gap between LLM conversations and long-term persistence without the complexity of building and hosting a full MCP server.

## What makes kits different from MCP servers

When you build a standard MCP server, you handle everything: the JSON-RPC transport, tool registration, authentication, database connections, deployment infrastructure. KitStack handles all of that. You write:

1. **Tool handlers** — functions that run when the LLM calls an action
2. **View components** — React UI that renders inside the LLM client
3. **A schema** — Drizzle table definitions for your database

KitStack provides the server, the router, the auth layer, the database provisioning, and the deployment pipeline. It's the difference between writing a React component and setting up a web server from scratch.

## How a kit runs

Your kit doesn't run as its own server. Instead, a single **MCP router** hosted by KitStack handles all kits:

1. An LLM client connects to the router via the MCP protocol.
2. The router authenticates the user and discovers which kits they've activated.
3. When the LLM calls a tool, the router dispatches to your kit's handler in a sandboxed Lambda.
4. Your handler queries the user's isolated database and returns a result.
5. The router forwards the result back to the LLM client.

Your kit code runs in a sandbox with minimal permissions — no database credentials in environment variables, no access to other kits' data.

## Two-tool progressive discovery

The MCP protocol has a scaling problem. Connect a few servers and you have dozens of tool definitions competing for the LLM's attention. Most clients now **defer** tool loading — hiding tools behind a search index until the LLM explicitly looks for them.

KitStack takes an entirely different approach. Instead of registering every action as a separate tool, all your kits are composed behind exactly **two MCP tools**: `kit` (for actions) and `kit_view` (for UI). The LLM drills down progressively:

```
kit()                    → list available kits
kit(id)                  → list actions in a kit (markdown table)
kit(id, cmd)             → describe an action's parameters (JSON Schema)
kit(id, cmd, params)     → run an action
```

This keeps one tool description in the system prompt instead of twelve. Once the LLM enters your kit, it stays focused there — no risk of mixing your tools with another server's, because the context boundary is explicit.

## Anatomy of a kit

Every kit is defined by a single `kit.config.ts` file:

```ts filename="kit.config.ts"
import { defineKit } from "@kitstackco/sdk";

export default defineKit({
  id: "crm",                           // Unique identifier (kebab-case)
  version: "1.0.0",                     // Semver
  name: "CRM Kit",                      // Human-readable name
  description: "Contacts, deals, pipeline",
  triggers: ["contact", "deal", "pipeline", "sales"],
  schema,                               // Drizzle table definitions
  migrationsDir: resolve(import.meta.dirname, "migrations"),
  instructions: crmInstructions,        // System prompt for the LLM
  tools: [addContact, listContacts, addDeal, ...],
  views: [contactsView, pipelineView, ...],
});
```

### Tools

Tools are the actions the LLM can take. Each tool has a name, a Zod argument schema, and a handler function. Tools can optionally separate data loading from presentation using the `load`/`handler` split — the same query powers both the tool's text response and a view's React component. See [Tools](/docs/concepts/tools) for details.

### Views

Views are stateful React components that render inside the LLM client as interactive iframes. Each view has a server-side loader and a client-side component that can display data, collect user input, call tools, and refresh itself. Views are optional — a kit with only tools works perfectly. See [Views](/docs/concepts/views) for details.

### Database

Every user gets their own SQLite database for each kit. Not row-level isolation — **completely separate databases**. You define your schema with Drizzle ORM and the SDK handles provisioning, migrations, and connection management. See [Database](/docs/concepts/database) for details.

### Triggers

The optional `triggers` field is an array of lowercase keywords that help LLMs route user requests to the right kit. Keep triggers short and specific — they're for intent matching, not descriptions.

### Instructions

The `instructions` field is a system prompt injected into the LLM's context when your kit is active. Use it to teach the LLM *when* to use each tool and *how* to interpret results.

## Kit lifecycle

| Phase | What happens |
|-------|-------------|
| **Define** | `defineKit()` validates naming conventions, descriptions, uniqueness |
| **Dev** | `kitstack dev` connects via relay, provisions a local DB, serves views in real-time |
| **Test** | `createTestKit()` runs against in-memory SQLite |
| **Build** | `kitstack build` bundles server + views, validates migrations |
| **Publish** | `kitstack publish` uploads to the KitStack marketplace |
| **Activate** | Users enable your kit with a single click — no setup required |

## Kit vs MCP server vs SaaS

| | Kit | MCP server | SaaS |
|---|---|---|---|
| **Complexity** | Utility tool — small, focused | Full application infrastructure | Complex business logic |
| **Data** | Per-user SQLite, managed by platform | Self-managed | Multi-tenant, self-managed |
| **Auth** | Handled by KitStack | You implement it | You implement it |
| **Deployment** | `kitstack publish` | Self-hosted or custom | Custom infrastructure |
| **Best for** | Personal tools, SME/enterprise utilities, bridging LLM and persistence | Custom integrations, complex workflows | Products with multi-user requirements, long-running tasks |
