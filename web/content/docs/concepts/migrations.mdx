# Migrations

This page covers the mechanics of migration generation and runtime behavior. For the broader data layer story — per-user databases, schema definition, and `ctx.db` — see [Database](/docs/concepts/database).

## Drizzle-kit integration

Migrations are generated from `src/schema.ts` by drizzle-kit into `migrations/`. You never write them by hand, but you do commit them.

When `drizzle.config.ts` exists in your kit root, these generate migrations automatically before running:

- `kitstack dev` and `kitstack call` — the kit's own `drizzle-kit generate`; a new migration is reported as one line on stderr (never stdout, so `--stdio` is safe)
- `kitstack build` and `kitstack deploy`
- `npm test` — the scaffolded script is `drizzle-kit generate && vitest run`
- `npm run generate` — just the generate step

`kitstack serve` and `serve()` do not generate migrations. If drizzle-kit is not installed, `dev` and `call` print a notice and use the existing files.

The scaffolded config:

```ts filename="drizzle.config.ts"
import type { Config } from "drizzle-kit";

export default {
  schema: "./src/schema.ts",
  out: "./migrations",
  dialect: "sqlite",
  dbCredentials: {
    url: "file:.kitstack/dev.db",
  },
} satisfies Config;
```

Edit `src/schema.ts`, then run `npm test` (or `kitstack dev` / `kitstack call`) — new migration files appear in `migrations/`. Commit the directory to git: it is what every runtime applies, including a self-hosted server.

## Raw SQL alternative

For non-Drizzle projects, use `migrationSql` instead of `migrationsDir`:

```ts filename="kit.config.ts"
export default defineKit({
  id: "my-kit",
  // ...
  migrationSql: `
    CREATE TABLE IF NOT EXISTS items (
      id TEXT PRIMARY KEY,
      name TEXT NOT NULL,
      created_at INTEGER NOT NULL
    );
  `,
});
```

`migrationSql` takes precedence if both fields are provided.

## Runtime behavior

| Context | What happens |
|---------|-------------|
| `kitstack dev`, `kitstack call` | Run `drizzle-kit generate`, then apply all migrations to `.kitstack/dev.db` |
| `kitstack build` | Same generate step, copies `migrations/` into build output, validates SQL |
| `createTestKit()` | Runs all statements against an in-memory SQLite database |
| `kitstack serve` | Applies all existing migrations on start (`CREATE TABLE IF NOT EXISTS`) |
| `serve()` | Applies nothing — see [Self-hosting: migrations](/docs/guides/self-hosting#migrations) |
| Hosted platform | The platform applies pending migrations per-user (migration tracking is a platform concern) |

<Note>
`kitstack dev` records which migration statements already ran against the local database, so each runs once. Tests always start from an in-memory database. To start over with an empty local database, use `kitstack dev --local --reset-db`. On the hosted platform, the platform handles migration state per-user.
</Note>

## Gotchas

**Migration SQL splitting is naive.** The runner splits on `;`. Semicolons inside string literals or trigger bodies will break it. In practice, kit migrations are simple DDL that never contains embedded semicolons.

**`IF NOT EXISTS` is auto-injected in dev mode.** The dev provisioner adds it to `CREATE TABLE` statements automatically.

**`reset()` in tests does not re-run migrations.** `createTestKit().reset()` clears data but keeps schema. Seed data won't be re-seeded.
