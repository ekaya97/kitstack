# Migrations

This page covers the mechanics of migration generation and runtime behavior. For the broader data layer story — per-user databases, schema definition, and the `db`/`ctx` parameters — see [Database](/docs/concepts/database).

## Drizzle-kit integration

When `drizzle.config.ts` exists in your kit root, `kitstack dev` and `kitstack build` both run `drizzle-kit generate` before proceeding. The typical config:

```ts filename="drizzle.config.ts"
import type { Config } from "drizzle-kit";

export default {
  schema: "./src/schema.ts",
  out: "./migrations",
  dialect: "sqlite",
  dbCredentials: {
    url: "file:.kitstack/dev.db",
  },
} satisfies Config;
```

Edit `src/schema.ts`, then run `kitstack dev` — new migration files appear in `migrations/`. The directory is committed to git.

## Raw SQL alternative

For non-Drizzle projects, use `migrationSql` instead of `migrationsDir`:

```ts filename="kit.config.ts"
export default defineKit({
  id: "my-kit",
  // ...
  migrationSql: `
    CREATE TABLE IF NOT EXISTS items (
      id TEXT PRIMARY KEY,
      name TEXT NOT NULL,
      created_at INTEGER NOT NULL
    );
  `,
});
```

`migrationSql` takes precedence if both fields are provided.

## Runtime behavior

| Context | What happens |
|---------|-------------|
| `kitstack dev` | Runs `drizzle-kit generate` if needed, then applies all migrations to `.kitstack/dev.db` |
| `kitstack build` | Same generate step, copies `migrations/` into build output, validates SQL |
| `createTestKit()` | Runs all statements against an in-memory SQLite database |
| Production | The platform applies pending migrations per-user (migration tracking is a platform concern) |

<Note>
The SDK does not track which migrations have been applied. In development and tests, the database is always fresh (local file or in-memory). In production, the platform handles migration state per-user.
</Note>

## Gotchas

**Migration SQL splitting is naive.** The runner splits on `;`. Semicolons inside string literals or trigger bodies will break it. In practice, kit migrations are simple DDL that never contains embedded semicolons.

**`IF NOT EXISTS` is auto-injected in dev mode.** The dev provisioner adds it to `CREATE TABLE` statements automatically.

**`reset()` in tests does not re-run migrations.** `createTestKit().reset()` clears data but keeps schema. Seed data won't be re-seeded.
