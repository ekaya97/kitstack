# Migrations

Every kit gets a per-user SQLite database. You define the schema in TypeScript with Drizzle ORM, and the SDK generates and applies migrations automatically.

## Schema as source of truth

Your Drizzle schema file is the canonical definition of your database:

```ts filename="src/schema.ts"
import { sqliteTable, text, real, integer } from "drizzle-orm/sqlite-core";

export const expenses = sqliteTable("expenses", {
  id: text("id").primaryKey(),
  date: text("date").notNull(),
  description: text("description").notNull(),
  amountGross: real("amount_gross").notNull(),
  category: text("category").notNull(),
  createdAt: integer("created_at", { mode: "timestamp" }).notNull(),
});

export const schema = { expenses };
```

Migrations are derived from this schema, not written by hand.

## How migrations work

### For Drizzle users (recommended)

The `migrations/` directory contains SQL files generated by `drizzle-kit`. The SDK integrates with drizzle-kit automatically:

```bash filename="Terminal"
# Edit src/schema.ts (add a column, table, etc.)
# Then run dev or build — drizzle-kit runs automatically
npx kitstack dev
```

When `drizzle.config.ts` exists in your kit root, `kitstack dev` and `kitstack build` both run `drizzle-kit generate` before proceeding. New migration files appear in `migrations/`.

Your kit's `kit.config.ts` references the directory:

```ts filename="kit.config.ts" highlight={5}
export default defineKit({
  id: "my-kit",
  // ...
  schema,
  migrationsDir: resolve(import.meta.dirname, "migrations"),
});
```

And the `drizzle.config.ts` (scaffolded by `kitstack init`):

```ts filename="drizzle.config.ts"
import type { Config } from "drizzle-kit";

export default {
  schema: "./src/schema.ts",
  out: "./migrations",
  dialect: "sqlite",
  dbCredentials: {
    url: "file:.kitstack/dev.db",
  },
} satisfies Config;
```

The `migrations/` directory is committed to git. It's a build input, not a build output.

### For non-Drizzle users

If you prefer raw SQL (or another ORM), use the `migrationSql` field instead:

```ts filename="kit.config.ts"
export default defineKit({
  id: "my-kit",
  // ...
  migrationSql: `
    CREATE TABLE IF NOT EXISTS items (
      id TEXT PRIMARY KEY,
      name TEXT NOT NULL,
      created_at INTEGER NOT NULL
    );
  `,
});
```

`migrationSql` takes precedence if both `migrationSql` and `migrationsDir` are provided.

## Runtime behavior

| Context | What happens |
|---------|-------------|
| `kitstack dev` | Runs `drizzle-kit generate` if needed, then applies all migrations to `.kitstack/dev.db` |
| `kitstack build` | Same generate step, copies `migrations/` into the build output |
| `createTestKit()` | Resolves migration SQL from `migrationsDir` or `migrationSql`, runs all statements against an in-memory SQLite database |
| Production | The platform applies pending migrations per-user (migration tracking is a platform concern) |

<Note>
The SDK does not track which migrations have been applied. In development and tests, the database is always fresh (local file or in-memory). In production, the platform handles migration state per-user.
</Note>

## Schema iteration during development

SQLite's `CREATE TABLE IF NOT EXISTS` is idempotent for the table name — but if you change column definitions, the existing table keeps its old schema.

<Warning>
When you change columns in `src/schema.ts`, you must reset your dev database. Run `kitstack dev --reset-db` or delete `.kitstack/dev.db` manually. Otherwise, the old table schema persists and your queries may fail or return incorrect data.
</Warning>

## Build-time validation

`kitstack build` validates your migration SQL against a fresh in-memory SQLite database:

- Each SQL statement is executed to verify syntax
- `DROP` statements are **rejected** with error code `MIGRATION_DROP_FORBIDDEN`
- Statement count is reported in the build output

```
  ✓ Migration SQL valid (8 statements)
```

<Warning>
DROP statements are forbidden in migration SQL. This is a hard rule — not configurable. If you need to remove a column or table, create a new table with the desired schema and migrate data.
</Warning>

## Gotchas

**Migration SQL splitting is naive.** The migration runner splits SQL on `;` characters. This means semicolons inside string literals or trigger bodies will break it. In practice, kit migrations are simple DDL (`CREATE TABLE`, `CREATE INDEX`) that never contains embedded semicolons.

**`IF NOT EXISTS` is auto-injected in dev mode.** The dev database provisioner automatically adds `IF NOT EXISTS` to `CREATE TABLE` statements, so drizzle-kit output (which omits it) works without modification.

**`reset()` in tests does not re-run migrations.** The `createTestKit().reset()` method uses `DELETE FROM` on each table — it clears data but keeps the schema. If your migrations include `INSERT` seed data, that data won't be re-seeded after `reset()`.
