# Tools

Tools are the actions an LLM can call in your kit. When a user says "add a contact" or "list my expenses", the LLM invokes a tool, your handler runs, and the result flows back into the conversation.

## Defining a tool

Every tool has three required fields: a `name`, a `description`, and an implementation (`handler` or `load`).

```ts filename="src/tools/add-contact.ts"
import { defineTool, kit } from "@kitstackco/sdk";
import { z } from "zod";
import { contacts } from "../schema";

export const addContact = defineTool({
  name: "add_contact",
  description: "Add a new contact to the CRM",
  mode: "act",
  args: z.object({
    name: z.string().describe("Contact's full name"),
    company: z.string().optional().describe("Company name"),
    email: z.string().optional().describe("Email address"),
  }),
  handler: async (ctx, args) => {
    const id = crypto.randomUUID();
    await ctx.db.insert(contacts).values({
      id,
      name: args.name,
      company: args.company ?? null,
      email: args.email ?? null,
    });
    return kit.result(kit.created(id, "contact", `Contact "${args.name}" added.`));
  },
});
```

The handler receives `ctx` (the request context: `ctx.db` is a Drizzle instance for the kit's database, `ctx.identity.principal` is the caller) and `args` (validated by Zod). See [Database](/docs/concepts/database) for how the database is provisioned.

## Mode and classification

| Field | Values | Default | Effect |
|-------|--------|---------|--------|
| `mode` | `"assist"` \| `"act"` | `"assist"` | `"assist"` reads or prepares; `"act"` changes state or has external side effects. Sets the MCP `readOnlyHint` and maps to the `kit:use` / `kit:act` grants on the hosted platform. |
| `classification` | `"public"`, `"internal"`, `"sensitive"`, `"destructive"`, or your own string | `"internal"` | Data sensitivity. `"destructive"` sets the MCP `destructiveHint`. |

Mark every write tool `mode: "act"`, as the scaffolded `add_item` does.

## The load/handler split

Many tools need the same data query in two places: the tool's text response and a view's React component. The `load` function extracts this shared query so both can reuse it.

```ts filename="src/tools/list-contacts.ts"
import type { KitContext } from "@kitstackco/sdk";

async function loadContacts(ctx: KitContext, args: { limit: number }) {
  return ctx.db.select().from(contacts).limit(args.limit);
}

export const listContacts = defineTool({
  name: "list_contacts",
  description: "List all contacts in the CRM",
  args: z.object({
    limit: z.number().optional().default(25).describe("Max results to return"),
  }),
  load: loadContacts,
  handler: async (ctx, args) => {
    const rows = await loadContacts(ctx, args);
    if (rows.length === 0) return kit.text("No contacts found.");
    const lines = rows.map((r) => `- ${r.name} (${r.company ?? "no company"})`);
    return kit.text(`**Contacts:**\n${lines.join("\n")}`);
  },
});
```

A view loader can then reuse the query: `listContacts.load(ctx, { limit: 100 })`. If you define `load` without a `handler`, the SDK auto-wraps it with `kit.json()`.

## Progressive discovery

The LLM doesn't see your individual tools directly. Instead, it sees the `kit` MCP tool — like a CLI entry point. Your action names are listed in the tool's description, and the LLM drills down through four levels:

| Call | Response |
|------|----------|
| `kit()` | List available kits |
| `kit(id: "crm")` | Markdown table of actions in the CRM kit |
| `kit(id: "crm", cmd: "add_contact")` | JSON Schema for `add_contact`'s arguments |
| `kit(id: "crm", cmd: "add_contact", params: { name: "Alice" })` | Runs the tool, returns the result |

This keeps one tool description in the system prompt instead of twelve. See [How kits work](/docs/concepts/kits) for the full rationale.

## Naming and validation rules

- Tool names **must** be `snake_case` (regex: `/^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$/`)
- Do not prefix tool names with the kit ID — the runtime namespaces automatically
- Tool descriptions must be at least 10 characters
- Every Zod field should have a `.describe()` call — these appear in the JSON Schema the LLM sees

## Runtime limits

<Warning>
On the hosted KitStack platform, all tools in a kit share a single Lambda runtime with **128 MB memory** and a **10-second timeout**. Every tool invocation — including the loader for views — must complete within 10 seconds and stay under 128 MB.
</Warning>
