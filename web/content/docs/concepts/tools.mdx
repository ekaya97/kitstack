# Tools

Tools are the actions an LLM can call in your kit. When a user says "add a contact" or "list my expenses", the LLM invokes a tool, your handler runs, and the result flows back into the conversation.

## Defining a tool

Every tool has three required fields: a `name`, a `description`, and an implementation (`handler` or `load`).

```ts filename="src/tools/add-contact.ts"
import { defineTool, kit } from "@kitstack/sdk";
import { z } from "zod";
import { contacts } from "../schema";
import { nanoid } from "nanoid";

export const addContact = defineTool({
  name: "add_contact",
  description: "Add a new contact to the CRM",
  args: z.object({
    name: z.string().describe("Contact's full name"),
    company: z.string().optional().describe("Company name"),
    email: z.string().optional().describe("Email address"),
  }),
  handler: async (db, args, ctx) => {
    const id = nanoid();
    await db.insert(contacts).values({
      id,
      name: args.name,
      company: args.company ?? null,
      email: args.email ?? null,
    });
    return kit.text(`Contact "${args.name}" added (ID: ${id}).`);
  },
});
```

### What the handler receives

| Parameter | Type | Description |
|-----------|------|-------------|
| `db` | `LibSQLDatabase` | A Drizzle database instance. Use your schema for type-safe queries. |
| `args` | Inferred from `z.object(...)` | Validated arguments. Zod runs before your handler is called. |
| `ctx` | `KitContext` | Contains `userId`, `kitId`, and optional `params`. |

### What the handler returns

A `KitToolResult` — created via the [`kit` helpers](/docs/api/kit-helpers):

- `kit.text("message")` — plain text response (reads only)
- `kit.result(kit.created(id, type, msg))` — structured write result with entity ID
- `kit.result(kit.updated(id, type, msg))` — structured update result
- `kit.result(kit.deleted(id, type, msg))` — structured delete result
- `kit.json(data)` — pretty-printed JSON
- `kit.error("message")` — error visible to the LLM (not a thrown exception)
- `kit.notFound("contact", id)` — standardized "not found" message

## The load/handler split

Many tools need the same data query in two places: the tool's text response and a view's React component. The `load` function extracts this shared query.

```ts filename="src/tools/list-contacts.ts"
import { defineTool, kit } from "@kitstack/sdk";
import { z } from "zod";
import { contacts } from "../schema";

async function loadContacts(db, args, ctx) {
  return db.select().from(contacts).limit(args.limit);
}

export const listContacts = defineTool({
  name: "list_contacts",
  description: "List all contacts in the CRM",
  args: z.object({
    limit: z.number().optional().default(25).describe("Max results to return"),
  }),
  load: loadContacts,
  handler: async (db, args, ctx) => {
    const rows = await loadContacts(db, args, ctx);
    if (rows.length === 0) return kit.text("No contacts found.");
    const lines = rows.map((r) => `- ${r.name} (${r.company ?? "no company"})`);
    return kit.text(`**Contacts:**\n${lines.join("\n")}`);
  },
});
```

Now a view loader can reuse the same query:

```ts filename="src/views/contacts/loader.ts"
import { defineLoader } from "@kitstack/sdk";
import { listContacts } from "../../tools/list-contacts";

export const loader = defineLoader(async (db, ctx) => {
  return listContacts.load(db, { limit: 100 }, ctx);
});
```

### Load-only tools

If you define `load` without a `handler`, the SDK auto-wraps it with `kit.json()`. The return value of `load` is serialized as formatted JSON.

```ts filename="src/tools/count-items.ts"
export const countItems = defineTool({
  name: "count_items",
  description: "Count all items in the database",
  args: z.object({}),
  load: async (db, args, ctx) => {
    const [row] = await db.select({ count: count() }).from(items);
    return { total: row.count };
  },
  // No handler — result is automatically JSON: { "total": 42 }
});
```

## Progressive discovery

The LLM doesn't see your individual tools directly. Instead, it sees a single `kit` MCP tool — like a CLI entry point. Your action names are listed in the tool's description, and the LLM drills down through four levels:

| Call | Response |
|------|----------|
| `kit()` | List available kits |
| `kit(id: "crm")` | Markdown table of actions in the CRM kit |
| `kit(id: "crm", cmd: "add_contact")` | JSON Schema for `add_contact`'s arguments |
| `kit(id: "crm", cmd: "add_contact", params: { name: "Alice" })` | Runs the tool, returns the result |

The `id` parameter selects which kit to target. This keeps one tool description in the system prompt instead of twelve, and once the LLM enters your kit, it stays focused there — no risk of mixing your tools with another server's. See [How kits work](/docs/concepts/kits) for the full rationale behind this design.

## Naming conventions

<Warning>
Tool names **must** be `snake_case`. The regex is `/^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$/`. Names like `addContact`, `Add-Contact`, or `_add_contact` will be rejected by `defineKit()`.
</Warning>

Do not prefix tool names with the kit ID. A tool named `add_contact` in a kit with ID `crm` is automatically namespaced as `crm/add_contact` in monolith mode. Naming it `crm_add_contact` would result in `crm/crm_add_contact`.

## Argument descriptions

Every Zod field should have a `.describe()` call. These descriptions appear in the JSON Schema that the LLM sees when it introspects a tool. Without them, the LLM has to guess what each parameter means.

```ts
// Good — the LLM knows exactly what to pass
args: z.object({
  sequenceId: z.string().describe("The sequence ID to delete"),
})

// Bad — the LLM might pass a prospect ID or email ID
args: z.object({
  id: z.string(),
})
```

<Warning>
Descriptions must be at least 10 characters. Short descriptions like "Adds stuff" tell the LLM nothing useful. Write descriptions that explain *when* and *why* to use the tool.
</Warning>

## Authorization

Tools can define an `authorize` hook that returns authorization requirements. These are checked before the handler runs.

```ts filename="src/tools/delete-deal.ts"
export const deleteDeal = defineTool({
  name: "delete_deal",
  description: "Delete a deal from the pipeline",
  args: z.object({ dealId: z.string().describe("The deal ID") }),
  authorize: (args, ctx) => [
    { relation: "owner", objectType: "deal", objectId: args.dealId },
  ],
  handler: async (db, args, ctx) => {
    await db.delete(deals).where(eq(deals.id, args.dealId));
    return kit.text("Deal deleted.");
  },
});
```

## Runtime limits

<Warning>
All tools in a kit share a single Lambda runtime with **128 MB memory** and a **10-second timeout**. Every tool invocation — including the loader for views — must complete within 10 seconds and stay under 128 MB. If your handler does heavy computation or returns very large result sets, split the work across multiple tool calls or paginate the output.
</Warning>
