# How to Build and Deploy

This guide covers the build pipeline, what it validates, and the two ways to run a kit in production: deployed to the hosted KitStack platform, or self-hosted on your own infrastructure.

<Note>
This guide assumes you've completed the [Getting Started](/docs/getting-started) tutorial and have a working kit.
</Note>

## Building your kit

```bash filename="Terminal"
npx kitstack build
```

The build runs locally and needs no account. It first runs `drizzle-kit generate` (if `drizzle.config.ts` exists), then these steps in order:

1. **Load** — imports `kit.config.ts`, running all `defineKit()` validations
2. **Validate migrations** — executes every SQL statement against an in-memory SQLite database
3. **Bundle server** — esbuild compiles your tool handlers into a single `kit.mjs`
4. **Generate view entries** — creates mount points for each view
5. **Bundle views** — Vite compiles React components into `vendor.js` + `shared.js` + per-view modules
6. **Compile CSS** — Tailwind processes `src/views/styles.css`
7. **Generate shell** — builds the MCP Apps HTML shell
8. **Write manifest** — `manifest.json` with hashes, sizes, SDK version

Output appears at `.kitstack/build/`:

```
.kitstack/build/
  kit.mjs           # Server bundle
  kit.zip           # Lambda archive
  manifest.json     # Build metadata
  shell.html        # MCP Apps shell
  views/
    vendor.js       # React + ReactDOM (shared)
    shared.js       # SDK hooks (shared)
    style.css       # Compiled Tailwind
    my-kit/
      dashboard.js  # Per-view module
      contacts.js
```

## Build validations

The build catches errors that `kitstack dev` intentionally skips for speed:

| Check | Error code | What it catches |
|-------|-----------|-----------------|
| Kit config loads | Various `TOOL_*`, `KIT_*` | Invalid names, short descriptions, duplicates |
| View.tsx files exist | — | Declared views without matching component files |
| Migration SQL valid | — | Syntax errors in SQL statements |
| No DROP statements | `MIGRATION_DROP_FORBIDDEN` | Destructive migration commands |
| Bundle size warnings | — | Server > 1MB, view modules > 500KB |

<Warning>
DROP statements are forbidden in migration SQL. This is a hard rule — not configurable. The build fails immediately with `MIGRATION_DROP_FORBIDDEN`.
</Warning>

### Bundle size tips

If you see size warnings:

- **Server bundle > 1MB** — check your esbuild externals. Heavy packages like `@libsql/client` should be externalized, not bundled.
- **View module > 500KB** — check your component's dependency tree. Import specific subpaths (e.g., `date-fns/format` instead of the full `date-fns` package).

## Deploying to the KitStack platform

Requires a KitStack account and the hosted KitStack API.

### Authenticate

```bash filename="Terminal"
npx kitstack login
```

This opens your browser to authenticate with your KitStack account. Credentials are saved to `~/.kitstack/credentials.json`.

### Deploy

```bash filename="Terminal"
npx kitstack deploy
```

`deploy` runs the full build itself, then uploads the artifacts (server bundle, views, shell) to the KitStack platform. You'll see:

```
  ✓ Kit "crm" deployed (private)
    Tools: 12
    Views: 5

  Activate it from your dashboard at https://kitstack.co/dashboard?tab=developer
```

Deployed kits are **private** — only you and the users you grant access can use them. If your organization requires approval, the deploy becomes a request that an admin approves with `kitstack deploy approve <request-id>`. Public marketplace listing (`kitstack publish`) is not available yet.

## Self-hosted deployment

To run your kit outside the KitStack platform, as your own MCP server, use [`kitstack serve`](/docs/cli/serve) or the programmatic [`serve()`](/docs/guides/self-hosting#programmatic-serve). No KitStack account is needed.

```bash filename="Terminal"
npx kitstack serve --transport http
#   http://127.0.0.1:3001/mcp
```

| Environment variable | Description | Default |
|---------------------|-------------|---------|
| `KITSTACK_TRANSPORT` | MCP transport (`stdio` or `http`) | `stdio` |
| `KITSTACK_PORT` | HTTP port | `3001` |
| `KITSTACK_MCP_PATH` | HTTP path of the MCP endpoint | `/mcp` |
| `KITSTACK_DB_URL` | libSQL database URL | `file:<kit>/.kitstack/dev.db` |
| `KITSTACK_DB_TOKEN` | libSQL auth token (for remote databases) | — |

`kitstack serve` binds to `127.0.0.1`, does not authenticate callers, and denies tools that declare `authorize` hooks. For a server other machines or users connect to — including in a container — write a small `server.ts` with `serve()` and its `host`, `authenticate`, and `checkAuthz` options. The [Self-hosting guide](/docs/guides/self-hosting) walks through it.

## Security defaults for hosted kit Lambdas

When deployed to the KitStack platform, kit Lambdas run with these security defaults:

| Setting | Value |
|---------|-------|
| Timeout | 10 seconds |
| Memory | 128 MB |
| Reserved concurrency | 5 |
| Network | VPC lockdown (no outbound internet) |
| Log retention | 3 days |

These defaults ensure sandboxed execution with minimal blast radius. On the hosted platform, kit handlers cannot make outbound HTTP requests or access external services. A self-hosted server has no such restriction.

## Gotchas

<Warning>
`kitstack deploy` requires authentication. Run `kitstack login` first. Credentials are stored at `~/.kitstack/credentials.json` and persist across sessions.
</Warning>
