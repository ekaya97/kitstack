# KitStack SDK

MCP is a powerful standard, but building with it today is rough. You need to learn the protocol, implement JSON-RPC, handle auth and OAuth, manage databases, set up deployment infrastructure, and troubleshoot client-specific quirks — before you even write your first tool.

KitStack abstracts all of that away. You write business logic and UI. The SDK handles the MCP protocol, the platform handles infrastructure. You don't need to understand how `tools/list` works, how tool descriptions affect LLM routing, or how different clients handle deferred loading. You define tools, define views, and deploy — KitStack handles the rest.

The current limitations of this approach (discovery overhead, permission granularity, client-dependent behavior) are subject to change as both KitStack and MCP standard adoption evolve. The framework insulates you from those changes — your kit code stays the same even as the underlying protocol and client landscape shifts.

## The kit philosophy

Every wave of computing shifts how users interact with software. The browser replaced desktop installers. Mobile put apps in pockets. Social media collapsed millions of websites into a single feed. Each time, developers who built for the new interface early had an outsized advantage.

We think AI is the next interface shift. Users increasingly don't want to learn 20 different tools — they want to describe what they need and have it happen. A single conversation that reaches into a CRM, logs an expense, drafts an outreach sequence, and tracks the follow-up. The MCP standard makes this possible, but building on it today still requires deep protocol knowledge and infrastructure work.

Kits are our answer to that. A kit is a small, focused app that lives behind an AI conversation — built by developers, for users who interact through natural language. KitStack handles the protocol, the infrastructure, and the deployment so you can focus on what you do best: writing the business logic and building the UI. The faster we can get MCP apps into users' hands, the faster this ecosystem grows.

## What is a kit?

A kit is a lightweight MCP app that bridges the gap between LLM conversations and long-term persistence. Not "memory" as a hack — a real database the LLM talks to.

Kits are utility tools. A CRM to track contacts and deals. An expense tracker. An outreach sequence builder. They handle the small stuff that doesn't warrant a full SaaS product but is too important to forget between conversations.

```ts filename="kit.config.ts"
import { defineKit, defineTool, kit } from "@kitstack/sdk";
import { z } from "zod";

const addItem = defineTool({
  name: "add_item",
  description: "Add a new item to the list",
  args: z.object({
    name: z.string().describe("Name of the item"),
  }),
  handler: async (db, args, ctx) => {
    return kit.text(`Item "${args.name}" added.`);
  },
});

export default defineKit({
  id: "my-kit",
  version: "1.0.0",
  name: "My Kit",
  description: "A simple item tracker",
  schema: {},
  migrationsDir: resolve(import.meta.dirname, "migrations"),
  instructions: "Use this kit to manage items for the user.",
  tools: [addItem],
});
```

Define your tools, define your kit, deploy. Start using it in any MCP-compatible LLM client.

## What makes KitStack different

### Two-tool progressive discovery

The MCP protocol has a scaling problem. Connect a few servers and you have dozens of tool definitions competing for the LLM's attention. Most clients now **defer** tool loading — hiding tools behind a search index until the LLM explicitly looks for them. This means your tool's description needs to win a keyword search before the LLM even knows it exists. And when different servers provide similar functionality (CRM tools from two providers, for example), the LLM starts mixing them in a single workflow — calling tool A to fetch data, then tool B to update it — leading to errors and confused outputs.

KitStack takes an entirely different approach. Instead of registering every action as a separate tool, all your kits are composed behind exactly **two MCP tools**: `kit` and `kit_view`. Users activate and deactivate kits whenever they want — the tool description is recomposed dynamically to reflect what's installed:

```
KitStack — 2 apps, 19 tools in one surface.
crm (contacts, deals, pipeline), expense (VAT, tax, receipts).
Call kit() to see all capabilities.
```

This front-loaded description lists every kit with its trigger keywords and every available action — giving the LLM enough signal to match your tools against user intent in a single search hit. Instead of matching individual actions, the LLM matches **workflows**. "Add a contact and create a deal" immediately routes to the CRM kit because the description contains both `add_contact` and `add_deal`. We believe LLMs are best at multi-step workflows, not single actions — and the description is optimized for that.

Once the LLM enters a kit, it works through actions progressively, like a CLI:

```
kit(id: "crm")                                        → show actions
kit(id: "crm", cmd: "add_contact")                    → describe parameters
kit(id: "crm", cmd: "add_contact", params: { ... })   → run it
```

The LLM can still switch between kits whenever it needs to — the escape hatch is always there. But the default behavior is focused, sequential work within one kit at a time, which matches how these tools are actually used.

### WYSIWYG development via relay

Run `kitstack dev` and get a public URL. No port forwarding, no tunnels, no local stdio setup. The relay serves your kit to any MCP client over the internet, and your view changes are served in real-time from your local Vite dev server — what you see is what's deployed.

```bash filename="Terminal"
npx kitstack dev
#   Relay connected. Session URL:
#   https://mcp.kitstack.co/dev/a3f2b1c8
```

Edit `View.tsx`, refresh the page, and your update appears immediately on the previous tool call. No need to ask the LLM again — the modules get hot-replaced on refresh. The dev experience is identical to the deployed experience.

### Isolated databases, zero complexity

Each user gets their own SQLite database for each kit. Completely separate — not row-level isolation, not shared tables, **different databases**. Regularly backed up. This eliminates the entire class of problems around LLM data access and permissions.

### One connection, dynamic kits

Traditional MCP marketplaces require a separate server connection per integration — each with its own OAuth flow, subscription, and reconnect cycle when things change. Activate a new connector and your client needs to reconnect to pick up the new tools.

KitStack is a single MCP connection. Users activate and deactivate kits from the dashboard without reconnecting their LLM client. The two-tool surface is static — `kit` and `kit_view` never change. What changes is the *description*, which is recomposed dynamically to reflect installed kits. The LLM sees your current kit catalog on every session with zero client-side configuration.

One auth, one connection, and the user manages what's available from a single dashboard — like an app store that doesn't require restarting the app after each install.

## Kit vs MCP server vs SaaS

| | Kit | MCP server | SaaS |
|---|---|---|---|
| **Complexity** | Utility tool — small, focused | Full application infrastructure | Complex business logic |
| **Data** | Per-user SQLite, managed by platform | Self-managed | Multi-tenant, self-managed |
| **Auth** | Handled by KitStack | You implement it | You implement it |
| **Deployment** | `kitstack publish` | Self-hosted or custom | Custom infrastructure |
| **Best for** | Personal tools, SME/enterprise utilities, bridging LLM and persistence | Custom integrations, complex workflows | Products with multi-user requirements, long-running tasks |

## Current limitations

**Discovery overhead.** Progressive discovery adds round trips compared to direct MCP tools. The LLM may need to call `kit(id)` to inspect available actions before running one. This is a deliberate trade-off — KitStack optimizes for multi-step workflows where one discovery call maps the full surface, not for single one-shot actions.

**Permission granularity.** Kit actions are not individual MCP tools, so MCP clients cannot enforce per-action permissions natively. KitStack enforces permissions server-side (allow or block per action category). A human-in-the-loop "ask before allow" pattern for sensitive actions is planned but not yet available — it requires an out-of-band confirmation channel that bypasses the LLM.

**Client behavior varies.** Some LLM clients defer tool loading behind a search index. KitStack's tool description is designed for this (trigger keywords and action names are front-loaded for search matching), but discoverability depends on how each client handles deferred tools. First-time discovery may require a search step; subsequent conversations benefit from the LLM caching kit information in memory.
